## 串行、依赖与内部分支

主管输出的是单个 `next`，不是下一组节点；直属成员执行结束后，固定边把控制权交回主管。每次成员调用是串行的。本实现用同步 `graph.stream` 运行嵌套组（agent_team.py:220-222），总主管等待整个所选评估组调用返回，再继续选择下一直属成员。评估员没有固定的 A→B→C 顺序，实际顺序由评估主管逐次选择；也不存在评估员间直接调度边。

系统没有 ROMA 式显式任务依赖 DAG，没有 `dependencies_graph` 的调度结构。这里存在的是**输入依赖和控制顺序**：评估使用候选答案，修订使用答案与评估反馈，再评估使用修订答案。原生提示词声明这些输入契约，图不额外检查每个契约已被满足。不能把“串行调用”描述成“评估员 B 必须使用评估员 A 的结果”。事实上，评估主管提示词要求向评估员传递答案时不带评估结果（mmlu.py:141），以减少互相影响；该内容保留在原生 BASE，并作为信息流审计记录，没有向 V2 加入详细通信操作规则。

叶子内部另有 ReAct 小图（react_agent.py:207-242,295-331）：模型调用→工具（有工具调用时）→模型调用；没有工具调用时进入输出整理，再返回组织主管。输出整理仍归属于该叶子角色，不增加一个组织节点。本领域实际工具均未设置 return_direct，故所测成员沿该回路完成。一般工具节点可能支持多个工具调用的内部并发，这与组织层一次调用一个成员不同；全局说明只把**组织层调用**称为串行，没有声称所有工具运行全局串行。

## BASE 的组织信息可见范围

离线完整输入样例位于 `.local/organization_v2/<domain>/normal_BASE_all_roles_inputs.json`。保留角色系统提示、传入背景、局部历史、消息 name、工具调用记录。工具定义和响应 schema 另在验证中作条件间相等检查。

| 角色 | BASE 明示/传入的信息 | 全局说明主要补充 |
| --- | --- | --- |
| 总主管 | 三个直属成员及职责、精确下一跳、生成与修订顺序要求 | 评估组内部完整成员、嵌套返回与全局调度联系 |
| 评估主管 | 本组成员、评价职责、上级、局部路由及重新评估接口 | 总主管的生成/修订分支、完成权限、跨分支反馈联系 |
| 生成者 | 自身职责、工具、输入/输出契约，上级名称随来信 name 传入 | 明确组织位置、其他分支及主管权限 |
| 修订者 | 自身职责、答案和反馈的输入契约、重新评估请求，上级消息 name | 反馈怎样通过总主管进入评估组，以及评估组的内部结构 |
| 各评估员 | 本人评判职责、工具、传入答案、上级来信 name | 本组其他成员、上层分支与完整返回关系 |

“消息元数据可见”“提示词明确讲解”和“模型能够推断”分别记录，不把后者当成可直接验证的事实。真实上级消息和后续结果还可能逐步透露全局关系。全部角色条件可能同时给部分叶子补上更明确的局部定位；评估主管拥有最清楚的局部信息前提。应按实际披露范围解释全部角色效果，不能假定各角色的局部信息完备程度相同。

## 交叉验证与边界

五个领域各运行九个场景：正常路径、修订重评、直接完成、跳过生成者、跳过修订者、跳过评估组、评估主管提前返回、只评部分成员、工具循环。每个场景对照原生路径、BASE 外部观察路径、V2 全部角色及 V2 仅评估主管，共 180 次原生离线 fixture 运行。V2 去除唯一前置说明后，每次输入都与对应原生输入相同；工具、响应 schema、路由、原生 CSV 结果相等，失败重试数为零。此结果验证外部干预没有无意改变协议，不估计真实模型准确率、成本或自然路由。

另使用真实 AzureChatOpenAI/SDK 的本地 HTTP mock，检查普通调用、工具绑定、结构化输出、工具绑定后结构化输出，以及原生总主管和评估主管的路由 schema，共六条路径。主管 schema 直接从原生 loadSuperviser 闭包中读取。SDK 请求体去掉新增首条系统消息后与原生相等，未连接服务、未使用真实凭据。真实服务认证、模型对长提示的服从和性能尚未测试。

原生修订提示中的“三个/四个评估员”残留属于决策细则，不作为组织图内容复制；它在 BASE/V2 中保持原样，本次未修改。外部超时和单领域进程边界继续保留；预算/异常导致的停止不被描述为组织的正常 FINISH 分支。
